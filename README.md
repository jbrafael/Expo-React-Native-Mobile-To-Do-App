# TaskFlow

A small offline To-Do app built with **Expo SDK 54 + React Native 0.81 + TypeScript (strict)**.
Tasks and categories are stored in SQLite (`expo-sqlite`), and due dates trigger **local** reminders through `expo-notifications`. There is no server and no push service.

- Create, edit, complete/reopen and delete tasks (title, description, category, optional due date + time)
- Manage categories (create, rename, delete). Deleting a category keeps its tasks and makes them uncategorized
- Filter by status (All / Pending / Completed) and category (Any / Uncategorized / a category)
- Local reminder at the due time ("Task reminder: <title>"), kept in sync on every change and re-checked at startup
- Data survives app restarts and device reboots

The full development history, including the failed attempts, is in [`BUILD_LOG.md`](BUILD_LOG.md). [`QUESTIONNAIRE.md`](QUESTIONNAIRE.md) answers the assignment's reverse-engineering questions.

## Run

### Quick path: Expo Go
```bash
npx expo start          # then press "a" (Android) or scan the QR code with Expo Go
```
Local notifications work in Expo Go. Expo Go logs an error saying *remote push* notifications were removed in SDK 53. This only affects remote push, which TaskFlow doesn't use, and the in-app toast is suppressed in `src/app/_layout.tsx`.

> **WSL2 note:** if `adb reverse` / `127.0.0.1:8081` cannot reach Metro, open `exp://<WSL-IP>:8081` on the emulator instead (`ip -4 addr show eth0`). See BUILD_LOG Entry 8.

### Native build (recommended for verifying notification lifecycle)
Expo Go hosts the app inside another app. For example, Expo Go's own boot receiver re-arms reminders after a reboot. A native build shows what TaskFlow itself does:

```bash
npm run android:native                       # = npx expo run:android (needs JDK 17 + Android SDK)
# or a self-contained release APK (JS bundle embedded, debug-signed):
npx expo prebuild --platform android
cd android && ./gradlew assembleRelease      # add -PreactNativeArchitectures=x86_64 to build one ABI
adb install app/build/outputs/apk/release/app-release.apk
# or in the cloud:
npx eas-cli@latest build --profile development --platform android
```
`android/` and `ios/` are generated by `expo prebuild` (Continuous Native Generation) and are git-ignored. Configure native behaviour in `app.json`, not in those folders.

## Checks and tests

```bash
npm run typecheck   # tsc --noEmit
npm run lint        # expo lint
npm test            # jest (jest-expo preset)
npx expo-doctor     # dependency/config validation
```

The test suite (42 tests) covers:
- **Repositories against real SQLite**: `better-sqlite3` runs behind a small adapter (`src/test/sqliteTestDb.ts`) that implements the expo-sqlite API subset. It covers migrations, CRUD, CHECK/UNIQUE constraints, the transactional category delete, and rollback.
- **Reminder lifecycle**: `src/notifications/__tests__/reminderLifecycle.test.ts` uses an in-memory fake of `expo-notifications`. It covers create/no-date/change/remove/complete/reopen/delete/past-date, duplicate-free reconciliation, permission denial, scheduling failure, and re-arming after a force-stop.
- **Editor screen (RNTL)**: empty-title validation, create, edit-by-id, not found.
- **Pure helpers**: filters and dates.

These tests check what the app *asks* the OS to do. Delivery was verified separately on emulators (see below).

## Architecture

```
src/
  app/                    Expo Router routes (screens only)
    _layout.tsx           SQLiteProvider (+ migrations) → TaskStoreProvider → native Stack; notification-tap handling
    index.tsx             Screen A – task list, filters
    task/[id].tsx         Screen B – editor (/task/new creates, /task/<id> edits)
    categories.tsx        Screen C – category management
  state/TaskStore.tsx     React Context + useTaskStore() hook: shared state and all mutations
  db/
    database.ts           schema, migrations (PRAGMA user_version), Db type
    taskRepository.ts     task SQL (parameterised)
    categoryRepository.ts category SQL, transactional delete
  notifications/reminders.ts  the only module that calls expo-notifications
  models/types.ts         Task, Category, TaskInput, filter types
  components/             Chip, TaskRow, DueDateField, PermissionBanner
  utils/                  filterTasks, date helpers
  theme/colors.ts         light/dark palette
  test/                   test-only SQLite adapter and notification fake
```

**Flow:** screen → `useTaskStore()` → repository (SQL) + reminder service → `expo-sqlite`.

- **State / refresh:** SQLite queries are not reactive. Every mutation in `TaskStore` writes through a repository, syncs the task's reminder, then calls `refresh()` to re-read tasks and categories into React state. Screens never run SQL. I used one Context because all three screens share the same lists; Redux or Zustand wasn't needed.
- **Navigation:** Expo Router native stack. Only the task **id** is passed (`router.push({ pathname: '/task/[id]', params: { id } })`), and the editor loads the task from SQLite. Unsaved edits are protected with `usePreventRemove` (header back, Android back, swipe).
- **Database:** `taskflow.db`; migrations run in `<SQLiteProvider onInit>` before any screen renders. Timestamps are ISO 8601 UTC strings.

| table | columns |
|---|---|
| `categories` | `id` PK, `name` TEXT NOT NULL UNIQUE COLLATE NOCASE (non-blank CHECK) |
| `tasks` | `id` PK, `title` TEXT NOT NULL (non-blank CHECK), `description`, `completed` 0/1, `due_date_time` ISO UTC, `created_at` ISO UTC, `category_id` → categories ON DELETE SET NULL, `notification_id` |

Category names are unique case-insensitively. Deleting a category runs `UPDATE tasks SET category_id = NULL …` and `DELETE FROM categories …` in one transaction.

## Notifications and permissions

- Reminder id = `task-<id>`. Scheduling always cancels that id first, so a task never has two reminders.
- A reminder exists only for a **pending** task whose due date is **in the future**. Completing, deleting, removing the due date, or moving it into the past cancels it. Reopening re-schedules it if the date is still in the future.
- **Startup reconciliation** (`reconcileReminders`) removes reminders for deleted/completed/past tasks and re-arms every eligible task. It re-arms instead of trusting `getAllScheduledNotificationsAsync()` because Android drops alarms on force-stop while the library's request store keeps listing them (BUILD_LOG Entry 9).
- **Android reboot:** expo-notifications registers a `BOOT_COMPLETED` receiver that re-arms stored requests. No custom native code is needed. Verified in Expo Go on an Android 8 emulator; see *Testing status*.
- **Permission:** requested the first time a reminder is actually needed, never at launch. On Android 13+ the Android channel `task-reminders` is created first, since the OS prompt needs a channel. If permission is denied, tasks are still saved, the user sees a message, and the list shows a banner with an "Open settings" link.
- **Exact timing:** `app.json` requests `SCHEDULE_EXACT_ALARM`. On Android 14+ this permission is denied by default for new installs, and the library falls back to inexact alarms, so a reminder may arrive a few minutes late.

## Known limitations

- **iOS was not tested** (no macOS/iOS device available). The code uses only cross-platform APIs, but iOS-specific behaviour hasn't been verified.
- No guarantee after **force-stop** until the app is opened again (Android drops the alarms and startup reconciliation re-arms them). The same applies to uninstall/reinstall, revoked permission, or aggressive OEM battery management.
- iOS allows at most 64 pending local notifications per app. That's fine for a personal To-Do list but isn't enforced.
- Web is not supported (expo-sqlite on web needs extra WASM/header setup).
- The past/future check uses the device clock. Changing the time zone keeps the absolute (UTC) due instant, so the displayed local time changes.
